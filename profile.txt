================================================================================
PROFILE — Brainstorming pagina profilo utente StockHub
================================================================================

OBIETTIVO
---------
Pagina `/profile`: area personale dell’utente **loggato**, con le proprie informazioni
generalmente utili in app (non l’elenco team — quello resta su `/staff`).

Campi target (MVP):
  • Nome e cognome (firstName + lastName) — visualizzazione + modifica
  • Email — solo lettura (cambio email = flusso verifica, post-MVP)
  • Ruolo applicativo (USER | ADMIN | SUPERADMIN) — solo lettura
  • Foto profilo — upload / anteprima / rimuovi
  • (~) Data registrazione (`createdAt`) — informativa

Obiettivo UX:
  • L’utente capisce chi è in app e può aggiornare nome e avatar senza passare da staff/admin.

Dove compare il **nome** utente (decisione UI)
-----------------------------------------------
  • **Dashboard** — saluto “Welcome back, {name}” via `getSession()` → `/api/auth/me` (nome dal DB).
  • **`/profile`** — header card + form (aggiornamento immediato dopo PATCH).
  • **Navbar** — **no nome** (solo link nav, icona messaggi, icona profilo, logout).

  Dopo PATCH nome: dashboard mostra il nome nuovo al prossimo visit (/me legge DB).
  Non serve rigenerare JWT né refresh sessione dedicato (ex 1.3).

Nota terminologia — Profile vs Staff
------------------------------------
  | Concetto        | `/profile`              | `/staff`                    |
  |-----------------|-------------------------|-----------------------------|
  | Scope           | Solo **utente corrente**| Tutto il team               |
  | Ruolo           | Lettura                 | Modifica solo SUPERADMIN    |
  | Email altrui    | No                      | Sì (lista team)             |
  | Foto            | Propria, modificabile   | No (solo chat / lista)      |
  | Online/Offline  | Non necessario in MVP   | Sì (presenza team)          |

Non confondere:
  • **Ruolo** = permessi (`User.role`) — in profilo badge read-only.
  • **Profilo** ≠ **Staff** — due pagine, due scopi.

CONTESTO TECNICO ATTUALE
-------------------------
Modello `User` (Prisma) — campi già presenti:
  id, firstName, lastName, email, emailVerified, image String?, role, lastSeenAt,
  createdAt, updatedAt, password?

  • `GET /api/auth/me` — leggero, per sessione UI: id, email, name, role.
    Non espone firstName/lastName separati, image, createdAt.
  • Modifica ruolo — già su `PATCH /api/staff/:id/role` (SUPERADMIN), non in profilo.
  • Upload immagini — pattern articoli: `api/src/lib/article-image.ts`, multer,
    file in `uploads/articles/`, serve via route dedicata.
    Stesso pattern riusabile per `uploads/users/` + `User.image` = storage key.

Raccomandazione API:
  • **`/api/auth/me`** — resta minimale (sessione, gate UI).
  • **`/api/profile`** — GET/PATCH/image per pagina profilo (dettaglio + edit).

API — bozza
-----------

GET /api/profile
  Auth: requireAuth
  Response: {
    user: {
      id, firstName, lastName, name, email, role,
      imageUrl,          // null se nessuna foto — URL pubblico API
      createdAt,         // ISO
      emailVerified      // ISO (informativo)
    }
  }

PATCH /api/profile
  Auth: requireAuth (solo proprio utente — sempre session.sub)
  Body: { firstName: string, lastName: string }
  Validazione Zod: trim, min 1, max ragionevole (es. 80)
  Response: { user: { ... come GET } }
  Nota: JWT cookie non va rigenerato — `/api/auth/me` legge firstName/lastName dal DB;
        dashboard e gate ruolo restano corretti al prossimo load pagina.

POST /api/profile/image
  Auth: requireAuth
  multipart/form-data, campo `image` (jpeg/png/webp, max 5 MB — allineato ad articoli)
  Salva in uploads/users/{userId}.{ext}, storage key in User.image
  Response: { user: { ..., imageUrl } }

DELETE /api/profile/image
  Auth: requireAuth
  Rimuove file + User.image = null

PATCH /api/profile/password
  Auth: requireAuth
  Body: { currentPassword, newPassword, confirmNewPassword }
  Validazione: min 8 caratteri nuova password; confirm deve coincidere;
               password attuale corretta; nuova diversa dalla attuale
  Response: { ok: true }

GET /api/profile/image  (o GET /api/users/:id/image — preferenza: /api/profile/image)
  Auth: requireAuth (solo propria immagine in MVP)
  Serve file con Content-Type corretto

Non esporre: password hash, token, lastSeenAt (opzionale in futuro).

Foto profilo — scelta tecnica
-----------------------------
  • Campo DB: `User.image` = storage key relativo (es. `users/clxyz.webp`).
  • Cartella: `uploads/users/` (parallel a `uploads/articles/`).
  • Helper: `api/src/lib/user-image.ts` (clone leggero di article-image).
  • Middleware upload: riusare pattern `article-upload.ts` → `profile-upload.ts`.
  • URL client: `/api/profile/image` (rewrite Next → Express).

Permessi
--------
  • Chi accede: qualsiasi utente **loggato** vede/modifica **solo il proprio** profilo.
  • SUPERADMIN non modifica ruolo da qui — resta su `/staff`.
  • Nessun accesso a profilo altrui via API profile (no :id in route MVP).
